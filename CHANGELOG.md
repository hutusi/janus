# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Commit id on dashboard run items** — the run list's Branch cell and the run page's meta line now show the short commit id next to the branch (`main a1b2c3d4`), so it's visible *which* commit a run executed — the branch alone is ambiguous once concurrency groups supersede runs or a force-push rewrites it. The id is the checkout-resolved SHA, so it's exact even for ref-only triggers; runs that haven't resolved a commit yet show just the branch.

- **Path filters** — [`paths` / `paths-ignore`](docs/pipeline-reference.md#path-filters) on `on.push` skip the whole run (terminal `skipped` + reason) when a push touched no matching files, and on a job skip just that job (and, transitively, jobs that `needs` it) — the monorepo staples: docs-only pushes skip CI, each service builds only when its subtree changed. Patterns are a GitHub-Actions-style glob subset (`*` per segment, `**` across segments, `?`); `paths` and `paths-ignore` are mutually exclusive per level like the branch filters. The changed set is a pure tree diff between the push's `before` and the checked-out head, so the depth-1 checkout design is unchanged (the base is fetched on demand, paid only by workflows that declare a filter) — and filters **fail open**: new branch, force-pushed-away base, undeterminable diff all run the pipeline rather than wrongly skip it. Push events only: `on.merge_request` rejects `paths` at validation (an MR needs merge-base history the shallow checkout avoids), and manual triggers and local `janus run` ignore path filters.

- **Numbered pagination on the dashboard run list** — the home page previously showed only the newest 50 runs with no way to reach older ones (the JSON API already paged via `?limit=&offset=`). It now pages 50 runs per `?page=N` with a numbered pager below the table; the current page's runs still drive the auto-refresh gating. Backed by a new `CountRuns` method on the store interface so the page count is exact in both the memory and file stores.

- **Version tag shown alongside the commit** — the dashboard header, `janus version`, and `/healthz` now display `v0.2.0 (f97e513)` instead of a raw `git describe` string. The tag and short commit are stamped as two separate ldflags vars (`main.version` / `main.commit`), so the tag no longer silently degrades to a bare commit hash in builds where git tags are absent (shallow CI clones). The run page header now shows the version too, like the run list. Builds that bypass the ldflags entirely (plain `go build` / `go install`) fall back to the version and commit the Go toolchain embeds on its own (Go ≥1.24) instead of reporting `dev`.

- **Janus medallion logo & favicon** — the dashboard gains a visual identity: a coin-style mark (the two-faced Janus bust in a ring, as on the Roman coin) rendered inline in both page headers, and served at `/favicon.svg` as the browser tab icon. One shared SVG template block is the single source for both — inline it follows the page's text color, standalone it uses the dashboard's status blue — so the binary stays the only artifact (no image files, no new routes beyond `GET /favicon.svg`).

- **Dashboard durations** — the run list gains a Duration column and the run page shows a duration on the run, each job, and each step, GitHub-Actions style (`12s`, `1m 23s`, `2h 5m 3s`; `—` for never-started). In-progress durations tick every second via a tiny inline script — anchored to server timestamps and advanced by a monotonic client delta, so a skewed browser clock can't distort them; finished durations are static server-rendered text, and pages without anything in progress register no timer. The run list also auto-refreshes every 5s while any listed run is still pending or running (the run page already refreshed every 2s).

- **Concurrency groups** — a workflow may declare a top-level [`concurrency:`](docs/pipeline-reference.md#concurrency-groups) key (mapping form only: `group:` + `cancel-in-progress:`): per expanded group, at most one run executes and one waits, a newer trigger supersedes the waiting run (`cancelled`, reason `superseded by run <id>`), and `cancel-in-progress: true` also cancels the executing one — so a burst of pushes runs the first and the newest, not every stale commit. "Newer" is trigger order (stamped when the trigger arrives), so checkouts finishing out of order can never let a stale commit supersede or outlive a newer run. `group:` templates over the closed token set minus `sha`/`short_sha` (rejected at validation: every run would be its own group, silently disabling the key); omitted, the group is the implicit `<name>-<branch|ref>`. Groups are always repo-scoped, so identical group strings in different repos never interfere. Daemon-only: `janus run` executes immediately and ignores the key.

- **Manual run cancellation** — `POST /api/runs/{id}/cancel` cancels a pending or running run: a queued run settles `cancelled` without executing (its never-started jobs recorded `skipped`), a running run has its step process groups killed. The run's `reason` records `cancelled via API`. The endpoint is token-mandatory like `/api/trigger` (it kills host processes; without `--api-token` it is disabled with `403`), answers `409` for already-finished runs, and its `202` is asynchronous and best-effort — a run whose last process exits concurrently still finishes on its own terms.

## [0.2.0] - 2026-07-22

### Added

- **Job-level `working-directory`** — a job may declare a default working directory for its steps, layered like `env:` (a step's own `working-directory` overrides it; `.` returns to the workspace root), so a job living in a subdirectory no longer repeats the key on every step. The job value gets the same treatment as the step value: `${{ }}` interpolation with the 4 KiB cap, resolution relative to the workspace, and the workspace-escape guard. Steps remain stateless shells — a `cd` inside one step still never affects the next.
- **Job-level branch filters** — jobs accept `branches:` / `branches-ignore:` with the same exact-match, allowlist-or-denylist semantics as `on:` filters, matched against the event's branch regardless of event kind (manual triggers included: the request's `branch` decides). A non-matching job — and, transitively, any job that `needs` one — is recorded `skipped` on the run instead of executed; if every job is filtered out the run itself finishes `skipped` with a reason. This is the supported way to run one pipeline with a branch-dependent tail (build everywhere, deploy only on `master`/`main`) without duplicating the build job across two files — and without an `if:`/expression language, which stays rejected.
- **Webhook deliveries log the clone URL before checkout** — each accepted delivery emits `webhook trigger accepted` with provider, event, repo URL, and branch before any git work begins. Previously nothing was logged until the trigger finished, so a checkout hanging (or running long) left no trace in the journal of what was being cloned. Logged clone URLs have embedded credentials stripped (`https://user:token@host/…` → `https://host/…`) so a credentialed URL never reaches the journal.
- **SSH clone URLs** — `clone_url` (`--clone-url`) selects which URL from the webhook payload a run checks out: `http` (the default, `git_http_url`) or `ssh` (`git_ssh_url`), for hosts that clone via deploy keys or cannot reach HTTPS. The selected URL *is* the run's repo URL end to end — what the allowlist gates, what the workspace clones, and what the run record shows — so it stays one string and the policy gate cannot drift from the fetch. ⚠️ Consequently `clone_url: ssh` requires rewriting `allow_repos` in the SSH form the platform emits: scp-style `git@host:group/repo` is matched opaquely and never cross-matches an `ssh://git@host/group/repo` entry. A payload that omits the selected field fails with `400` naming it, rather than silently falling back to the other transport and surfacing later as a confusing `403`.
- **Run-history retention** — a new `history_limit` (`--history-limit`) caps how many terminal runs are kept; when exceeded, the oldest terminal runs and their logs are pruned after each run finishes and at startup (running/pending runs are never pruned). It **defaults to 1000** (`0` = unlimited) so installs are bounded out of the box — see the Changed note about the first-startup prune. This also bounds the flat-file store's list/startup cost, which reads every run directory.
- **Run-list pagination** — `GET /api/runs` accepts `?offset=` alongside `?limit=`, returning a newest-first window so clients can page through history.
- **Persistent workspaces** — `workspace_strategy: persistent` (`--workspace-strategy`) gives each repo one reusable janus-owned workspace, updated in place with `git fetch` + `git reset --hard`, so untracked dependency and build caches (`node_modules`, incremental output) survive between runs — hermeticity deliberately traded for speed, opt-in only. Concurrent runs of one repo are serialized by a per-repo try-lock; a contending trigger falls back to a fresh per-run clone rather than blocking. `persist-*` directories survive restarts and the startup sweep; any git failure in the reuse path self-heals by rebuilding the directory. `fresh` (per-run directories) remains the default.
- **Scripted uninstall** — `deploy/install.sh uninstall` (or `make uninstall-service`) stops and disables the service and removes the unit and binary, keeping `/etc/janus`, `/var/lib/janus`, and the `janus` user so no data or secrets are destroyed by surprise; `--purge` removes those too. Supports `--dry-run` like the installer.
- **`make install` / `make uninstall` / `make install-service`** — `make install` places the built binary in `$(PREFIX)/bin` (default `/usr/local/bin`; `DESTDIR` supported), and `make install-service` provisions the Linux systemd service from the local build by wrapping `deploy/install.sh --binary` (extra script flags via `INSTALL_FLAGS="..."`). `install` deliberately does not rebuild, so `sudo make install` never runs the Go toolchain as root.
- **`branches-ignore` trigger filter** — `on.push` and `on.merge_request` accept `branches-ignore: [...]`: run on every branch except the listed ones (exact string match, like `branches`). Declaring both `branches` and `branches-ignore` on one trigger is a validation error — pick an allowlist or a denylist.
- **Per-trigger pipeline file** — `POST /api/trigger` accepts an optional `pipeline_path` field selecting a committed pipeline file other than the configured default for that one run, named relative to the configured file's directory (`"release.yml"` → `.janus/release.yml`; subdirectories allowed). Absolute paths and `..` escapes are rejected with `400` before anything is cloned, and the override is recorded on the run's event, so `GET /api/runs/{id}` shows which file ran. Webhooks select a file the same way via a `?pipeline_path=` query parameter on the webhook URL (an invalid value answers `200 {"status":"error"}` so the platform doesn't auto-disable the hook); without it they use the server-wide `pipeline_path`.
- **Windows support** — pipeline steps can run on native Windows. The step shell now depends on the host (`/bin/sh` on unix, `cmd` on Windows) and is overridable with a new step [`shell:`](docs/pipeline-reference.md#step-shell) key (`sh`/`bash`/`cmd`/`powershell`/`pwsh`). A `janus-windows-<arch>.exe` binary is published, and a `windows-latest` CI job guards execution (process-tree kill uses the built-in `taskkill`, so no new dependency). Pipelines are no longer portable across OSes; the systemd unit and `deploy/install.sh` remain Linux-only.
- **Scripted install** — [`deploy/install.sh`](deploy/install.sh) provisions Janus as a systemd service in one command: it detects the architecture, downloads and checksum-verifies the release binary, creates the `janus` user, writes an idempotent config plus a `janus.env` with generated secrets, and enables the unit. Supports `--allow-repo`, `--version`, `--dry-run`, and an `upgrade` mode; linted by `shellcheck` in CI.
- **Offline install** — `deploy/install.sh --binary <path>` installs a locally-built binary and makes no network access at all (no release download or remote checksum), for air-gapped hosts. `upgrade` accepts it too.
- **Linux deployment** — a hardened `systemd` unit ([`deploy/janus.service`](deploy/janus.service)) and secret template ([`deploy/janus.env.example`](deploy/janus.env.example)), plus a [deployment guide](docs/deployment.md) for running Janus as a dedicated-user service.
- **Example pipelines** — [`examples/ci.yml`](examples/ci.yml) (build the pushed branch on every push; publish to a separate pages repo on `master`/`main`), plus [`examples/build.yml`](examples/build.yml) + [`examples/release.yml`](examples/release.yml) as the split-file variant of the same project, with an [`examples/README.md`](examples/README.md) covering both models, the push-vs-MR-merge trigger, the shallow checkout, and host SSH auth. Validated in CI.

### Changed

- ⚠️ **Webhook and manual-trigger responses no longer wait for the checkout** — `runner.Trigger` records a pending run and answers `202 {"status":"accepted","run_id":...}` immediately; checkout, pipeline parse, and `on:` matching happen in the background with the outcome recorded on the run: `failed` + reason for a checkout/pipeline error, `skipped` + reason for a non-matching event (a new `reason` field on the run record explains pre-execution terminal states, shown on the dashboard run page). The webhook's former `200 {"status":"error"}` / `200 {"status":"ignored"}` bodies and the manual API's `400` for checkout/parse failures are gone — poll `GET /api/runs/{id}` or the dashboard for the outcome. Non-matching pushes now leave terminal `skipped` records; like all terminal runs they are pruned by `history_limit`.
- **`GET /api/runs` returns compact run summaries** — the list endpoint (and the HTML dashboard) now returns run summaries (`id`, `workflow_name`, `event`, `status`, timestamps) without the per-step `jobs`/commands, so listing, pruning, and startup reconciliation never hold every full record in memory. Full detail (including jobs) remains at `GET /api/runs/{id}`.
- **`history_limit` now defaults to 1000 (was unlimited).** ⚠️ On the first startup after upgrading, terminal runs beyond the newest 1000 — and their logs — are pruned at startup and after each subsequent run. Set `history_limit: 0` (or `--history-limit 0`) to keep unlimited retention. This bounds the default **run count** and the flat-file store's per-list scan — **not total disk**: `history_limit` never prunes a running run, and a single runaway step log can still grow without limit, so bound disk with OS quotas. A time-sorted index to *eliminate* the scan remains possible future work.
- **Pipelines have generous structural limits** — a pipeline may declare at most 256 jobs, 256 steps per job, a 256-character job name, and a 64 KiB step `run`; beyond that it is a validation error. The limits sit far above any real pipeline and exist only to keep per-run artifacts and the dashboard finite for pathological input.
- **Job names are restricted to `[A-Za-z0-9_-]`** — previously any map key was accepted, but the store derives each step's log-file name from the job name via a lossy sanitizer, so distinct names like `a/b` and `a?b` collapsed to the same file and interleaved their logs. Pipelines using other characters in job names must rename them.
- **Examples restructured around two models** — a new merged [`examples/ci.yml`](examples/ci.yml) (named for where it lives in a repo, `.janus/ci.yml`) leads: it triggers on every push, always builds the pushed branch, and its `deploy` job carries a job-level `branches: [master, main]` filter — on other branches the deploy is recorded `skipped` while the build runs. `examples/build.yml` + `examples/release.yml` remain as the split-file model (complementary `on:` filters covering `main` as well as `master`), routed per hook via a second webhook with `?pipeline_path=release.yml` or run on demand — the README explains both and when to pick which. All three build Janus's **pinned, verified checkout as-is**: the former "re-fetch the branch tip" first step is gone, since it could build a newer commit than the run's recorded SHA (a newer push triggers its own run), silently breaking run-identity — the README explains why not to reintroduce it.

### Fixed

- **Steps that fail to start name the reason in their log** — a missing `working-directory` or an absent shell binary previously produced a failed step with exit `-1` and an *empty* log, leaving nothing to diagnose. The failure is now written to the step log as a `janus: …` line (naming the working directory explicitly when it is the cause — the raw OS error blames the shell binary even then), matching how interpolation and workspace-escape failures already report.
- **Slow checkouts no longer fail webhook deliveries** — GitLab.com's fixed ~10-second webhook timeout raced the formerly synchronous checkout: a clone slower than the timeout made the platform hang up, and because the checkout ran under the request context the hangup *cancelled the in-flight checkout* (`checkout: … context canceled`), so jittery latency to the git host produced intermittent delivery failures with no run recorded. The delivery is now answered before any git work begins, and a client hangup can no longer cancel a checkout the caller was just told is underway.
- **Checkouts fail fast instead of hanging on interactive git prompts or dead connections** — the workspace now runs git with `GIT_TERMINAL_PROMPT=0` plus, when the operator configured nothing themselves, two defaults: `GIT_SSH_COMMAND=ssh -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=4` (skipped if `GIT_SSH_COMMAND`/`GIT_SSH` is set **or** `core.sshCommand` is configured in gitconfig) and a set-but-empty `GIT_ASKPASS` (skipped if `GIT_ASKPASS` or `core.askpass` is configured), which disables askpass resolution so credential requests fail immediately on the blocked terminal path — `GIT_TERMINAL_PROMPT` alone does not stop askpass helpers, so a blocking helper could otherwise pin a checkout slot. The gitconfig probes run inside the workspace being checked out, so workspace-local config and `includeIf "gitdir:"` rules are honored and an unrelated repository around the daemon's own working directory can never suppress the hardening. With `clone_url: ssh`, a host missing from `known_hosts`, a key needing a passphrase, an unreachable advertised `git_ssh_url` (e.g. a Docker-internal hostname), or a mid-transfer stall previously pinned the checkout (and its admission slot) until the 10-minute checkout deadline with nothing to show for it. Prompts now fail immediately, an unreachable host in ~10s, and a stalled connection in ~60s, each recording the ssh error (`Host key verification failed.`, `Permission denied`, `Connection timed out`) as the failed run's reason. Host keys are still strictly verified — nothing is auto-accepted; batch mode also disables ssh password auth, which a daemon could never type anyway. Anything the operator configured — environment (`GIT_SSH_COMMAND`/`GIT_SSH`/`GIT_ASKPASS`, matched case-insensitively on Windows, whose environment is case-insensitive) or gitconfig (`core.sshCommand`/`core.askpass`) — is respected verbatim and must itself be non-interactive (include `-o BatchMode=yes` in a custom ssh command).
- **Records that can be written can always be read back** — the run-record write now enforces the same size cap as the read, and the last uncapped event field (`title`) is length-capped at ingestion, so a large GitLab commit/MR title can no longer produce a `run.json` that `SaveRun` writes but `GetRun` refuses (which made the run vanish from listing/detail/reconciliation).
- **Listing no longer loads every full run into memory** — `ListRuns` (dashboard, API, pruning, startup reconciliation) now scans compact summaries instead of materializing every full record, so a large history can't require gigabytes of memory to page or reconcile.
- **Listing reads compact summary sidecars, not full records** — the file store writes a tiny `summary.json` beside each `run.json`, and listing/pruning/reconciliation read only those, so a large history no longer drives O(total) disk reads / JSON parsing on the unauthenticated dashboard. `run.json` stays the source of truth (written first); a missing/legacy sidecar self-heals on first read, and reconciliation re-checks the full record so a lagging sidecar can never mislabel a finished run.
- **Interpolation can't expand into gigabytes** — `${{ ... }}` substitution is now bounded: the materialized command (≤1 MiB), working-directory (≤4 KiB), each environment value (≤64 KiB), and the total environment (≤1 MiB) are capped, and a step whose interpolation would exceed them fails with an error instead of OOMing the shared daemon (previously a ~500 KB env value referenced thousands of times in a valid 1 MiB pipeline could expand to gigabytes).
- **Event fields are length-capped at ingestion** — `repo_url` (≤2 KiB), `ref`/`branch`/`pipeline_path` (≤512 B) are rejected when over-long before any work, so a large webhook field can't inflate the stored run, the unauthenticated dashboard, or interpolation. The dashboard also truncates branch/workflow/needs it renders consistently, and the file store caps a `run.json` read so a corrupt/oversized record errors instead of loading whole.
- **Storage failures are retriable, not dropped** — when the store can't record a run (a full/read-only data dir), `Trigger` now returns a typed `ErrStoreUnavailable`, so the webhook answers `503` + `Retry-After` (GitLab retries instead of the event being acknowledged with `200` and lost) and the manual trigger answers `503` (not a misleading `400`), alongside the degraded `/healthz`.
- **The run page bounds disk reads, not just output** — the log renderer now stops iterating as soon as the page byte budget is spent, so a run with a huge number of steps can no longer make one unauthenticated request read the entire log set from disk (gigabytes) just to emit ~1 MiB.
- **Pipeline files are size-capped at ingestion** — a `.janus/ci.yml` over 1 MiB is rejected when read, before it is loaded into memory or parsed, which bounds everything derived from it (commands, names, env, job/step counts) at the source rather than field by field. The dashboard also truncates long commands and names it renders, so a large value stored on an older run can't bloat the page.
- **HTML run page is hard-bounded** — the run page's log region is now rendered through a byte-limited writer, so step headers, truncation markers, and tails all count against the total budget (a huge job name in a header can no longer overflow it), and the file store's log tail is read via an `io.SectionReader` bound to the size observed at open, so a concurrently-growing log can't turn a tail read into a head read or overshoot the cap. Pipeline validation also rejects absurd structure — more than 256 jobs, 256 steps/job, a 256-character job name, or a 64 KiB step `run` — so the unauthenticated page (and per-run artifacts) stay finite regardless of input.
- **Storage failures consistently degrade `/healthz`** — a `SaveRun` failure (a full/read-only data dir) now latches the daemon degraded too, so a store that breaks with no interrupted runs to reconcile reports `503` instead of a false `200` while rejecting every trigger.
- **Allowlist rejects backslash traversal** — the dot-segment guard now splits on `\` as well as `/` and rejects `%5c`, so `…/acme/x\..\..\evil` (and its percent-encoded form) can no longer slip past a group-level entry on backends that treat backslash as a path separator.
- **HTML run-page logs are strictly bounded** — the run page's log tail now reads through an `io.LimitReader`, so a still-growing step log can no longer overshoot the per-step cap between the size check and the read, and the whole page is capped by a total byte budget (across all steps), so a run with a very large step count can't produce a huge unauthenticated page. The truncation marker is now driven by an exact "log was longer" flag from the store, so a log exactly at the cap is no longer mislabeled truncated.
- **Degraded health can no longer be falsely cleared by a restart** — the daemon now also marks itself degraded when startup reconciliation fails against an unwritable store, so restarting with storage still full/read-only reports `503` instead of a false `200`. (A restart clears the latch, but the failing startup step re-latches it while storage stays broken.)
- **Checkout is deadlined and cancellable by the request** — a checkout now runs under a 10-minute deadline and is aborted by request cancellation as well as shutdown, so a stalled or malicious git server can no longer pin an HTTP handler and an admission slot until the daemon stops, and a webhook client that times out mid-checkout no longer leaves a started run for its retry to duplicate. Execution still uses the runner's own context (it survives the request). Invalid-SHA/ref triggers also no longer leak empty `run-*` workspace directories.
- **Persist-failure after retries is no longer silent** — once the terminal-write retries are exhausted, `janus run` exits non-zero (the steps ran, but the final state could not be persisted) and the daemon's `/healthz` returns `503 {"status":"degraded"}` (latched until restart), so monitoring and restart reconciliation stop trusting a stale success.
- **HTML run page renders a bounded log tail** — the unauthenticated, auto-refreshing run page previously buffered every step's entire log on each 2-second refresh; it now renders only the last 64 KiB per step (with a truncation marker pointing at the full logs), so a large or still-growing run's log can no longer OOM the daemon. The `?follow=1` stream and `/api/runs/{id}/logs` snapshot are unchanged.
- **Whole-run log snapshots stream instead of buffering** — `GET /api/runs/{id}/logs` (the aggregate view) previously read every step's log fully into memory via `io.ReadAll`; it now streams each step directly to the response, bounding memory for large runs.
- **Terminal run-state writes are retried before the record is abandoned** — a transient failure (full or briefly read-only disk) persisting a run's *final* status would strand the stored run non-terminal forever, which startup reconciliation then records as `cancelled` even for a run that actually succeeded. The terminal write now retries a few times before giving up.
- **Allowlist distinguishes git authorities** — URL normalization now keeps userinfo, so `ssh://git@host/acme` no longer matches `ssh://root@host/acme` (git connects as different users), and `git://`'s default port is corrected to 9418 (was treated as ssh's 22).
- **Manual-trigger JSON rejects all trailing data** — the trailing-data check used `encoding/json`'s `Decoder.More()`, which returns false for a trailing `]`/`}`, so `{…}]` slipped through; it now requires a second decode to reach `io.EOF`, matching the strict YAML parsers.
- **Installer fails when the service is active but never serves** — after ten failed health probes (curl present) the installer warned and returned success, then announced Janus "running"; it now aborts the install with a `journalctl` pointer.
- **Git option injection through trigger-supplied SHA/ref closed** — a manual trigger or webhook could set `sha`/`ref` to values git parses as options (e.g. `--upload-pack=/bin/sh`), executing an arbitrary program during `git fetch` and bypassing the commit verification. The workspace now validates the SHA as 7–64 hex characters and the ref against a conservative git-ref grammar before any git process runs (rejecting leading `-`, `..`, `@{`, trailing `.lock`/`/`, and the like). The 7-char SHA minimum also rejects ambiguously short prefixes. Each run now records the full resolved `HEAD`, so metadata, `${{ sha }}`, and `JANUS_SHA` name the exact 40-char commit even for abbreviated or ref-only triggers.
- **Graceful shutdown tracks and cancels checkout/parse work** — admission now enrolls a trigger in the shutdown wait *before* the checkout, and the checkout runs on the runner's context, so a shutdown that times out mid-checkout waits for (and then kills) the git process instead of returning while it runs on. This also removes a `sync.WaitGroup` misuse where `Add` could be called after `Wait` had returned. New triggers are rejected with `503` once shutdown begins.
- **Installer verification fails on an inactive service** — `deploy/install.sh` printed `systemctl is-active`'s output but discarded its exit code, so with curl unavailable (offline `--binary` installs) verification reported success even when the service never started. An inactive service now aborts with a pointer to `journalctl`.
- **Log following no longer re-reads the whole file every poll** — the `?follow=1` stream re-read the entire log from disk every 300ms and discarded the already-sent prefix, an O(n²) disk workload for long chatty steps. `Store.ReadLogs` now takes a byte offset (file store seeks; memory store slices), and the follower reads only what appended since the last tick.
- **Crash-orphaned runs no longer display as running forever** — runs left `pending`/`running` by a crashed or hard-killed daemon are marked `cancelled` at the next startup (running jobs/steps → `cancelled`, never-started work → `skipped`), so the dashboard stops refreshing them indefinitely and log followers terminate.
- **Graceful shutdown always stops build processes** — if HTTP shutdown exceeded its 10s deadline (one lingering log-follow connection sufficed), `janus serve` returned without ever cancelling in-flight runs, exiting with build process groups still alive — contradicting the drain behavior the systemd unit documents. The runner now shuts down unconditionally. `janus run` similarly ignored Ctrl-C: it now wires the signal into the engine so interruption drives the process-group kill and the run is recorded `cancelled`.
- **Externally-cancelled runs are recorded as `cancelled`, not `failed`** — shutdown/interrupt previously coarsened the run status to `failed` even though jobs and steps already used `cancelled`; a fail-fast run (one job genuinely failing) still reports `failed`. A failure to persist a run's *terminal* state is now logged at error level (there is no later write to self-heal it); intermediate persist failures remain warnings.
- **Trigger bursts can no longer start unbounded work** — checkout, pipeline parsing, and the pending-run queue now count against a bounded admission pool (4× `max_parallel_runs`; previously only *executing* runs were capped, so a burst could spawn unlimited git processes and workspaces). When the pool is full, webhooks and `POST /api/trigger` answer `503` with `Retry-After` so providers retry the delivery instead of piling up.
- **HTTP request hardening** — the webhook body cap now rejects oversized payloads with `413` instead of silently truncating them into a misleading signature failure (`401`); `POST /api/trigger` gets a 1 MiB body cap, rejects unknown JSON fields and trailing data, and the server sets `ReadTimeout`/`IdleTimeout` so a slow request body cannot pin a connection open indefinitely (`WriteTimeout` stays unset deliberately — log following is a long-lived response).
- **Strict parsing gaps closed** — a pipeline or config file containing a second YAML document (`---`) is now an error instead of the extra document being silently ignored; an unterminated `${{` placeholder is now a validation error instead of reaching the shell verbatim; and `janus serve` rejects nonsense configuration at startup (negative `max_parallel_runs`/`max_parallel_jobs`/`step_timeout`, explicitly empty `workspace_root`/`pipeline_path`) instead of silently reverting to defaults — notably a negative `step_timeout` used to mean *no timeout*.
- **Checkout can no longer silently run a different commit than the trigger records** — when a Git server refuses fetch-by-SHA, the checkout falls back to fetching the ref; if the branch moved (or was rewritten) between the webhook and the checkout, Janus would execute the new tip while the run's metadata, `${{ sha }}`, and `JANUS_SHA` still named the event's commit. Both fresh and reused (persistent) checkouts now verify `HEAD` against the requested SHA and fail the run on a mismatch. Abbreviated SHAs from `janus run` match by prefix.
- **Allowlist path traversal closed** — repo URLs containing `.` or `..` path segments, literal or percent-encoded (`%2e`, `%2f`, `%25`), are now always denied: git, HTTP infrastructure, or the filesystem could resolve such segments *after* the prefix match, letting `https://host/acme/../evil/repo` slip past a `https://host/acme` entry (worse for local-path remotes, where `..` walks the real filesystem). Allowlist entries containing them are now a startup error.
- **systemd hardening now actually applies** — the balanced sandbox in [`deploy/janus.service`](deploy/janus.service) had trailing inline comments on its directive lines, which systemd parses as part of the value and silently ignores. `NoNewPrivileges`, `ProtectSystem`, `ProtectHome` and `PrivateTmp` were all being dropped (confirmed via `systemctl show`); the comments moved to their own lines so every protection takes effect. CI now rejects inline-comment directives in `deploy/*.service`.

## [0.1.0] - 2026-06-26

### Added

- **Pipeline engine & CLI** — a small GitHub-Actions-flavored `.janus/ci.yml` with strict validation (unsupported keys and expressions are errors, not features), a DAG scheduler that runs independent jobs concurrently and is fail-fast, and a host-process step executor that streams combined stdout/stderr to the store. `janus validate <file>` and `janus run <dir>`.
- **Server & triggers** — `janus serve` exposes a GitLab webhook endpoint (push + merge request), a manual HTTP trigger, a JSON API, and a read-only HTML dashboard. Each run shallow-checks-out the triggering commit into a per-run workspace.
- **Persistence** — a restart-safe flat-file run/log store, plus an in-memory store for the CLI and tests.
- **Hardening** — per-step process-group kill, step timeouts, run/job concurrency caps, graceful shutdown, and bearer auth on `/api` (mandatory for `POST /api/trigger`).
- **YAML config file** — `--config` (and auto-load of `./janus.yml`) covering all `janus serve` settings, with precedence defaults < file < env < flags. `janus init` scaffolds an annotated `janus.yml`.
- **Repository allowlist** (`allow_repos`) — deny-by-default with a `*` allow-all escape hatch; a repo not on the list is rejected with `403` before any checkout. Defense-in-depth against a leaked webhook secret or API token.
- **`CLAUDE.md`** — concise guidance for AI coding agents.
- **MIT license.**

### Changed

- The example config now defaults `data_dir`/`workspace_root` to a cwd-relative `./janus-data` (created on demand, no sudo) instead of `/var/lib/janus`.
